# Руководство оператора

Руководство для тех, кто устанавливает, настраивает и сопровождает bAD (blazerity Asset Discovery) в своей сети.

| Компонент | Текущая версия | Где посмотреть |
|-----------|----------------|----------------|
| Сервер (панель и API) | 2.0.1 | файл `VERSION`, `GET /v1/health`, подвал панели |
| Агент (MSI на ПК) | 2.0.1 | файл `agent/VERSION`, поле `agent_version` в карточке устройства |

Версии сервера и агента независимы. Обновление панели и обновление агентов — разные процедуры (см. разделы 4 и 5).

**Путь целиком:** установить сервер → настроить HTTPS → получить enrollment-токен → установить MSI на ПК → увидеть устройство в панели.

## Важные правила

| # | Правило | Почему |
|---|---------|--------|
| 1 | Сертификат лучше загрузить через панель, а не передавать при установке | Панель работает без сертификата в режиме HTTP bootstrap, и сертификат можно добавить позже без переустановки |
| 2 | Дамп БД не содержит ключи шифрования | Для восстановления нужен site bundle или отдельная копия ключей (см. раздел 6) |
| 3 | После массовой установки агентов смените enrollment-токен | Старый токен позволяет регистрировать новые ПК, пока он действует |

База данных работает только на **PostgreSQL** (`BAD_DATABASE_URL` в `site.env`). Ключи шифрования и сессий хранятся в `/etc/bad/*`, а не в базе.

## 1. Установка сервера (Debian 12)

### 1.1. Запуск установщика

Установщик — `deploy/debian/install.sh`, требует root.

```bash
BAD_DOMAIN=bad.example.com \
  sudo -E bash deploy/debian/install.sh
```

Установщик выполняет шесть шагов:

1. Установка пакетов, включая `postgresql` и `postgresql-client`.
2. Создание пользователя, каталогов и virtualenv.
3. Создание локальной базы PostgreSQL, применение схемы и запись `BAD_DATABASE_URL`. PostgreSQL слушает только localhost.
4. Настройка службы `bad-api` (systemd).
5. Настройка nginx.
6. Вывод памятки «что дальше».

В конце установщик один раз выводит enrollment-токен и admin API-токен. Сохраните их: они также хранятся в `/etc/bad/site.env`.

Если переменные `BAD_TLS_CERT` и `BAD_TLS_KEY` не заданы, nginx работает только по HTTP на порту 80. Это нормальный режим на время настройки, см. 1.2.

### 1.2. Режим HTTP bootstrap и загрузка сертификата в панели

Основной путь настройки:

1. Откройте `http://bad.example.com/login` **только из доверенной сети** (LAN, VPN или `ssh -L`).
2. Войдите как `admin` / `admin` и **сразу смените пароль** (`/account/password`).
3. Загрузите сертификат и ключ: **Параметры → Сертификат** (`/settings/tls`).
4. Откройте `https://bad.example.com`, войдите заново.
5. Только после этого устанавливайте агенты с `SERVERURL=https://…`.

Пока сервер работает по HTTP, не публикуйте панель в интернет и не выполняйте на нём ничего из списка ниже:

- установка агентов;
- экспорт site bundle;
- ввод боевых паролей LDAP и SMTP;
- ротация enrollment-токена.

Проверка здоровья сервера:

```bash
curl -fsS http://bad.example.com/v1/health    # режим bootstrap
curl -fsS https://bad.example.com/v1/health   # после настройки TLS
# → {"status":"ok","version":"2.0.1"}
```

### 1.3. Сертификат TLS в панели

Страница: **Параметры → Сертификат** (`/settings/tls`), доступна только администратору.

На странице отображаются:

- режим: «HTTP bootstrap» или «HTTPS активен»;
- домен `BAD_DOMAIN` (только чтение);
- наличие файлов fullchain и privkey на диске (сам ключ в интерфейсе не показывается);
- данные установленного сертификата: Subject, Issuer, Not after, SAN, fingerprint и время последнего применения.

Файлы на диске:

| Файл | Путь |
|------|------|
| Цепочка (leaf и промежуточные) | `/etc/bad/tls/fullchain.pem` |
| Закрытый ключ | `/etc/bad/tls/privkey.pem` |
| Промежуточный каталог до применения | `/etc/bad/tls/staging/` |

**Загрузка или замена сертификата:**

1. Откройте **Параметры → Сертификат**.
2. В блоке «Загрузить сертификат и ключ» вставьте PEM-сертификат и приватный ключ. Цепочку промежуточных сертификатов добавьте при необходимости.
3. Нажмите «Установить и перезагрузить nginx».

Панель проверяет PEM и соответствие ключа сертификату, затем кладёт файлы в staging и через systemd-helper (`bad-tls-apply`) выполняет `nginx -t` и перезагрузку nginx. Если проверка не прошла, боевые файлы не меняются, а причина показывается в интерфейсе.

После успешного применения:

- появляется режим «HTTPS активен»;
- HTTP (порт 80) перенаправляется на HTTPS;
- включается HSTS;
- cookie сессии получает флаг `Secure` (`BAD_COOKIE_SECURE=auto`).

Повторная загрузка сертификата выполняет ротацию тем же способом.

Повторно применить сертификат вручную: `systemctl start bad-tls-apply.service`. Логи: `journalctl -u bad-tls-apply`.

Автоматический выпуск сертификатов (Let's Encrypt / ACME) не поддерживается. Смена `BAD_DOMAIN` из интерфейса также не поддерживается.

**Правила работы с ключом:**

- не коммитьте ключ и не кладите его в общие каталоги;
- не пересылайте `privkey.pem` в тикетах и чатах;
- не редактируйте `/etc/bad/tls/*` вручную во время загрузки через панель.

### 1.4. Установка сразу с TLS

Если сертификат уже лежит на сервере, его можно передать установщику. Имя (CN или SAN) должно совпадать с `BAD_DOMAIN`.

```bash
BAD_DOMAIN=bad.example.com \
BAD_TLS_CERT=/etc/ssl/certs/bad.fullchain.pem \
BAD_TLS_KEY=/etc/ssl/private/bad.privkey.pem \
  sudo -E bash deploy/debian/install.sh
```

Дальнейшая настройка такая же, как в разделе 1.2, только сразу по HTTPS.

### 1.5. Первый вход

1. Откройте адрес из вывода установщика (`http://…/login` или `https://…/login`).
2. Войдите как `admin` / `admin`.
3. Смените пароль на странице `/account/password`. До смены панель открывает только страницу смены пароля и выход.

Вход работает без LDAP. Admin API-токен для браузера не используется: это отдельный механизм для интеграций.

Токены и настройки хранятся в `/etc/bad/site.env` (права `640`, владелец `root:bad`).

uvicorn слушает только `127.0.0.1:8000`, TLS обрабатывает nginx.

**Ограничения входа и регистрации.** Стандартная конфигурация nginx передаёт приложению реальный IP клиента. По нему работают ограничения частоты входа и регистрации агентов. Если вы ставите собственный прокси перед bAD, настройте передачу IP так же, как в шаблоне `deploy/debian/nginx/bad.conf.template`.

### 1.6. LDAP (опционально)

1. Войдите как локальный администратор.
2. Откройте **Параметры → LDAP** (`/settings/ldap`).
3. Укажите: хост, порт, SSL или StartTLS, bind DN и пароль, базу поиска пользователей, шаблон фильтра (должен содержать `{username}`), атрибут отображаемого имени и роль по умолчанию.
4. Сохраните и нажмите «Проверить подключение».
5. Включите вход через LDAP.

Пользователи каталога входят через `/login`. Сначала проверяются локальные учётные записи.

Пароль bind хранится в базе в зашифрованном виде и после сохранения не показывается. Чтобы его не менять, оставьте поле пустым.

По умолчанию соединение с LDAP защищено (LDAPS или StartTLS) с обязательной проверкой сертификата. Отключить проверку (`tls_insecure`) можно только в лаборатории.

## 2. Агент на Windows (MSI)

### 2.1. Установка

Имя файла: `bad-agent-<версия>.msi`, версия указана в `agent/VERSION`. MSI собирается на Windows (см. `installer/msi/README.md`).

```powershell
msiexec /i bad-agent-2.0.1.msi `
  SERVERURL=https://bad.example.com `
  ENROLLMENTTOKEN=<enrollment-токен> `
  /qn
```

Файлы агента: **`%ProgramFiles%\blazerity\bad agent\`** (`bin\`, `bad.cmd`). Служба Windows: **`badagent`** (в списке служб — **bAD Agent**).

Каталог с `bad` по умолчанию добавляется в системный `PATH` (`ADDPATH=1`). Чтобы не менять `PATH`, добавьте `ADDPATH=0`.

```powershell
msiexec /i bad-agent-2.0.1.msi `
  SERVERURL=https://bad.example.com `
  ENROLLMENTTOKEN=<enrollment-токен> `
  ADDPATH=0 `
  /qn
```

**Безопасность токена.** Установщик не передаёт enrollment-токен через скрипты PowerShell, но токен всё равно может попасть в командную строку `msiexec` и в подробные логи установки. Не пересылайте такие логи в чаты и тикеты. После массовой установки смените токен (раздел 2.4).

### 2.2. Что делает агент

- Работает как служба **`badagent`** и запускается автоматически.
- Регистрируется на сервере один раз и сохраняет API-ключ в `%ProgramData%\blazerity\bAD\config.json`.
- Отправляет полный снимок инвентаризации при старте и далее по расписанию (по умолчанию каждые 6 часов).
- Отправляет heartbeat каждые 15 минут.
- Проверяет обновления при старте службы и далее раз в 24 часа. MSI скачивается **только с вашего сервера**, а не с GitHub.

Целевую версию задают политики: `update_target` — «последняя» или закреплённая.

Обновление MSI не требует повторной регистрации: `ProgramData` сохраняется.

**Апгрейд с агента 1.x на 2.0.** Установите MSI **2.0.0** поверх старой версии (тот же `msiexec` или self-update с сервера). Установщик сам остановит службу **`BlazerityAssetDiscovery`**, уберёт каталог **`%ProgramFiles%\blazerity\bAD\`** и запустит **`badagent`**. Настройки в **`%ProgramData%\blazerity\bAD\`** сохраняются, повторный enroll не нужен. Подробнее: [release-notes-agent-2.0.0.md](release-notes-agent-2.0.0.md).

### 2.3. Локальная команда `bad`

Сервер для локальных отчётов не нужен.

| Команда | Кто может запускать | Что делает |
|---------|---------------------|------------|
| `bad` | любой пользователь | текстовый отчёт |
| `bad -r` | любой пользователь | HTML-отчёт |
| `bad -h` | любой пользователь | справка |
| `bad -c` | администратор | интерактивная настройка |
| `bad config set <ключ> <значение>` | администратор | задать параметр |
| `bad config unset <ключ>` | администратор | сбросить параметр |
| `bad push` | администратор | синхронизация с сервером: очередь, инвентаризация, heartbeat |
| `bad update` | администратор | проверить и установить MSI с сервера |
| `bad service …` | администратор | управление службой `badagent` |

Управление службой (от администратора):

```powershell
bad service status|start|stop|restart
```

Справка по командам: `bad -h`.

Параметр, заданный локально через `bad -c` или `bad config set`, в панели помечается как «задано на агенте». Значения API-ключа и enrollment-токена через CLI не задаются и не выводятся.

### 2.4. Смена enrollment-токена после массовой установки

Смена токена **обязательна**, если MSI установили на много ПК или токен мог попасть в лог. Старый токен перестаёт работать для **новых** регистраций. Уже зарегистрированные устройства не затрагиваются: их API-ключи лежат в `ProgramData`.

Шаги:

1. Откройте **Параметры → Обновления агента** (`/settings/updates`), раздел «Enrollment token».
2. Нажмите «Сменить enrollment token» и подтвердите действие.
3. Сохраните новый токен (он показывается один раз).
4. Скопируйте готовую команду `msiexec` со страницы и обновите ею Intune или GPO.

Ротацию делайте по HTTPS. Restart `bad-api` не нужен.

Автоматизация: `POST /v1/admin/enrollment/rotate` с admin-токеном (см. [api-v1.md](api-v1.md)). Новый токен в ответе возвращается один раз.

После смены регистрация со старым токеном возвращает `401`. ПК, которые не успели зарегистрироваться, переустановите MSI с новым `ENROLLMENTTOKEN`.

### 2.5. Переустановка Windows (reimage)

Чистая переустановка Windows создаёт **новое устройство** в панели: у машины новый MachineGuid, поэтому агент регистрируется заново, и появляется новая карточка. Агент не склеивает карточки автоматически.

Что делать:

- **Найти дубликаты.** На карточке устройства показываются возможные дубли по имени узла, серийным номерам, SMBIOS, диску и т. д. Заглушки вроде «все F» или «все нули» в серийниках **не** считаются совпадением (с сервера **1.10.1**). Это подсказка, а не кнопка слияния.
- **Архивировать старую карточку.** Если слияние не нужно, архивируйте или удалите старую карточку вручную.
- **Слить карточки (администратор).** Кнопка появляется, только если совпадают сильные признаки: серийный номер корпуса или SMBIOS UUID, либо два из трёх признаков: BIOS, IdentifyingNumber, плата. Донор должен быть в статусе «устарел» или «в архиве». После слияния история переносится на основную карточку, донор отправляется в архив, создаётся событие `device_merged`.

Слияние по одному имени узла или по одному диску не предлагается. Не сливайте две активные карточки, которые обе онлайн.

Обновление MSI без переустановки Windows сохраняет `ProgramData`, повторная регистрация не нужна.

## 3. Работа в веб-панели

### 3.1. Мастер первых шагов

Пока настройка не завершена, на странице **Обзор** (`/`) показывается блок «Первый запуск» с шагами: пароль, сертификат, первое устройство. Прогресс доступен по `GET /setup/progress.json` для авторизованной сессии.

Агенты ставьте только после перехода на HTTPS.

### 3.2. Обзор и дашборд

- **Обзор** (`/`): поле **«Поиск по парку»** (от двух символов — устройства и события); блок **«Требует действия»** по умолчанию свёрнут (если пунктов не больше двух — открыт); мастер «Первый запуск» и ops-сигналы (см. раздел 7).
- **Дашборд** (`/dashboard`): сверху короткая сводка (активные, онлайн, устаревшие, архив), ниже графики и блок «Парк».

Обе страницы используют одну сводку по парку и открываются быстро. С **2.0.1** интерфейс панели в стиле **Bolt** (сетки Обзора и Дашборда, обновлённые списки и Параметры). Подробнее: [release-notes-2.0.1.md](release-notes-2.0.1.md).

### 3.3. Список устройств

Страница: `/devices`.

- Поиск по имени узла, `device_id` и серийному номеру.
- Фильтры по тегу, волне и архиву; страницы внизу таблицы (по 50 записей).
- Кнопка «Сбросить фильтры» появляется, когда фильтры активны.
- Массовые действия: отметьте строки и отправьте устройства в архив или добавьте тег.
- Если парк пуст, сверху показывается ссылка на страницу с токеном и MSI.
- Рядом с именем узла отображается иконка типа корпуса (ноутбук, ПК, сервер и т. д.).

На карточке устройства доступно:

- теги (через запятую);
- список событий и последний снимок инвентаризации;
- копирование серийных номеров, IPv4 и MAC-адресов;
- отзыв и ротация ключа, архивация, удаление записи из панели;
- **«Снять агент с компьютера»** (только admin): в поле подтверждения введите **точное имя узла** (как в карточке; если имени нет — `device_id`). После отправки команда уходит агенту при **следующем heartbeat** (обычно до ~15 минут). Программа удаляется с ПК через MSI; **карточка устройства в панели остаётся**, это не отзыв API-ключа. Пока статус «Удаляется», команду можно **отменить**. Нужен агент **2.0.1** или новее. Подробности: [tz-remote-uninstall.md](tz-remote-uninstall.md).
- кнопка «Обновить политику и версию»: агент при следующем heartbeat заново применит политику и проверит MSI;
- список возможных дубликатов (см. 2.5).

Теги матчатся политиками: условия `tag equals` и `tag contains`.

### 3.4. События

Страница `/events` показывает изменения по парку, новые сверху. Есть пагинация, поиск по тексту и фильтр по важности.

Важность: `medium`, `high`, `critical`. По умолчанию показываются события от `medium` и выше, `all` показывает все. Строка ведёт на страницу **`/events/номер`**: карточка события, **ссылка для копирования**, переход к устройству. В списке и в API ленты тяжёлые детали не дублируются — они в карточке и в последнем снимке.

### 3.5. Время в интерфейсе

В панели и в HTML-отчёте (`bad -r`) время показывается относительно («5 мин. назад»). Точное локальное время выводится в подсказке. В API и базе время хранится только в UTC (ISO 8601).

### 3.6. Порог «устарело»

Устройство считается устаревшим, если нет связи дольше заданного времени. Порог задаётся в **Параметры → Хранение и очистка**. Если он не задан, используется `BAD_DEVICE_STALE_AFTER_SECONDS` (по умолчанию 3600 секунд). Рекомендуемое значение — примерно в два раза больше интервала heartbeat агента (по умолчанию 15 минут).

## 4. Обновление сервера из GitHub

Страница: **Параметры → Обновление сервера** (`/settings/server-update`). Это обновление панели и API (линия версий сервера, файл `VERSION`), а не MSI агентов.

| Шаг | Что происходит |
|-----|----------------|
| Выбор ветки | По умолчанию `main`. Можно выбрать ветку из списка GitHub или ввести её вручную. |
| Проверить обновления | Сравнивает установленную версию (ветка и sha) с последним коммитом выбранной ветки. |
| Установить | Скачивает коммит в `/var/lib/bad/server-releases/`, переключает `/opt/bad` и перезапускает `bad-api`. |

Установка выполняется через systemd-helper (`bad-server-update-apply`), пароль sudo в панели не требуется. Обновление сервера не меняет агент и MSI.

**Откат.** Сохраняется до трёх предыдущих успешных версий. В таблице слотов нажмите «Откатить».

**Токен GitHub.** Задаётся в `BAD_GITHUB_TOKEN` (`/etc/bad/site.env`) или в файле `/etc/bad/github_token` (права `440`). Интерфейс показывает только, задан ли токен.

| Что нужно | Права |
|-----------|-------|
| Проверка и загрузка кода | `contents:read` |
| Сборка MSI на GitHub (кнопка) | дополнительно `actions:write` |

Для публичного репозитория токен на чтение необязателен, для сборки MSI нужен всегда. Предпочтительны токены с минимальными правами или GitHub App, а не classic-токен с полным доступом.

**Сборка MSI на GitHub.** Кнопка «Собрать MSI на GitHub» запускает workflow `release-msi`, дожидается результата и добавляет MSI в зеркало агента. Подписывать MSI не обязательно.

## 5. Обновления агента: зеркало MSI и выбор версии

Страница: **Параметры → Обновления агента** (`/settings/updates`).

Агенты всегда скачивают MSI только с вашего сервера. Файлы хранятся в каталоге вида `…/agent-updates/<версия>/bad-agent-<версия>.msi`.

### 5.1. Загрузка MSI (air-gap)

1. Откройте `/settings/updates`.
2. В блоке «Загрузить MSI (air-gap)» выберите файл `bad-agent-X.Y.Z.msi`. Манифест JSON и SHA-256 можно не указывать: сервер посчитает их сам.
3. Нажмите «Подгрузить в зеркало».
4. Версия появится в «Каталоге версий» с источником (`upload` или `github`), SHA-256 и временем загрузки.

У каждой строки доступны кнопки:

- **Latest**: назначить версию последней;
- **Удалить**: нельзя удалить версию, которая является latest или закреплена политикой.

Синхронизация с GitHub: кнопка «Синхронизировать сейчас» (`POST /settings/updates/sync`). Статус и интервал синхронизации показаны вверху страницы.

### 5.2. Что ставить: `update_target`

| Значение | Поведение |
|----------|-----------|
| `latest` (последняя в зеркале) | Агенты ставят версию latest. Если назначить latest более старую версию, агенты откатятся. |
| Конкретная версия `X.Y.Z` | Агенты ставят указанную версию. Если её нет в зеркале, агент ничего не делает, а на Обзоре появится предупреждение. |

Задать значение можно в **Параметры → Политики** или переопределить на карточке устройства. Параметр `update_enabled=false` отключает обновление агента.

Агент следует рекомендации сервера, поэтому поддерживаются и обновление, и откат.

## 6. Резервные копии и восстановление

Есть три разных артефакта. **Дамп базы не содержит ключи.**

| Артефакт | Что внутри | Для чего |
|----------|-----------|----------|
| Ежедневный дамп | `pg_dump -Fc` → `bad-YYYY-MM-DD.dump` в `BAD_BACKUP_DIR` | данные; без ключей полного восстановления не будет |
| Копия ключей | `/etc/bad/data_key` и `/etc/bad/session_secret` | хранить отдельно от дампа; права `440`, владелец `root:bad` |
| Site bundle | `bad.dump` + ключи + метаданные зеркала | полное восстановление |

Не копируйте каталог данных PostgreSQL как резервную копию.

**Скачать site bundle:** **Параметры → Резервные копии** → «Скачать site bundle». Работает только по HTTPS.

**Копия ключей вручную:**

```bash
sudo install -d -m 700 /root/bad-key-escrow
sudo tar -C /etc/bad -czf /root/bad-key-escrow/bad-keys-$(date -u +%Y%m%d).tar.gz data_key session_secret
sudo chmod 600 /root/bad-key-escrow/*
```

**Восстановление из site bundle:**

```bash
sudo bash deploy/debian/restore-site-bundle.sh /path/to/bad-site-bundle-….tar.gz
```

Скрипт останавливает `bad-api`, восстанавливает базу и ключи в `/etc/bad` и запускает сервис. После восстановления проверьте `/v1/health`, вход в панель и при необходимости зеркало MSI.

Проводите пробное восстановление до того, как понадобится оно на практике.

Права: дампы и каталог бэкапов доступны только владельцу сервиса (`600`/`700`). Не храните site bundle в общих папках и не коммитьте `/etc/bad/*`.

## 7. Сигналы на Обзоре

На странице `/` кроме обычных счётчиков показываются:

- пустое зеркало MSI или не назначена latest-версия;
- устройства, которые отстают от целевой версии;
- закреплённая версия отсутствует в зеркале;
- отозванные устройства, которые не в архиве (нужна ротация ключа или восстановление).

## 8. Интеграции через API

Внешние системы (например, 1C Itilium) читают данные по HTTP JSON API `/v1` с admin-токеном в заголовке `Authorization: Bearer`. Cookie браузерной сессии и ключи агентов для этого не подходят.

Полное описание: [api-v1.md](api-v1.md).

Admin-токен выводится при установке и хранится в `/etc/bad/site.env` (`BAD_ADMIN_TOKEN`). Вызывайте API только по HTTPS.

Пример:

```bash
curl -fsS -H "Authorization: Bearer <admin-token>" \
  https://bad.example.com/v1/devices

curl -fsS -H "Authorization: Bearer <admin-token>" \
  'https://bad.example.com/v1/events?limit=50'
```

## 9. Безопасность: чеклист оператора

- [ ] Сменили пароль `admin` сразу после установки.
- [ ] Загрузили сертификат и работаете только по HTTPS.
- [ ] Агенты устанавливаются только с `SERVERURL=https://…`.
- [ ] Сменили enrollment-токен после массовой установки и обновили Intune или GPO.
- [ ] Копия ключей (`data_key`, `session_secret`) хранится отдельно от дампа базы.
- [ ] Site bundle, дампы и файл `site.env` доступны только администраторам.
- [ ] Порт uvicorn (8000) не открыт наружу: доступ идёт через nginx.
- [ ] Логи установки MSI не пересылаются в чаты и тикеты.

**Базы и ключи.** Ключи лежат вне базы: `/etc/bad/data_key` и `/etc/bad/session_secret`. Если ключи находятся в базе (старые установки), дамп базы содержит всё нужное для расшифровки, и его нужно защищать как секрет.

**Cookie и HTTP.** До загрузки сертификата cookie работает по HTTP (`BAD_COOKIE_SECURE=auto`). После применения сертификата включаются HTTPS, HSTS и флаг `Secure`. Агенты не должны подключаться по HTTP.

**Тестовые стенды без TLS.** Для лаборатории можно запустить uvicorn на Linux (см. `server/README.md`) и агент с `BAD_ALLOW_HTTP=1` на `http://127.0.0.1:8000`. Не используйте такую конфигурацию в продуктиве.

## 10. Устранение неполадок

| Симптом | Что проверить |
|---------|---------------|
| Агент не регистрируется, `403` на `/v1/enroll` | Адрес `SERVERURL` должен быть `https://`. При включённом TLS регистрация по HTTP запрещена. |
| `401` на `/v1/enroll` | Токен устарел после смены. Используйте текущий токен из раздела 2.4. |
| MSI не устанавливается, в `%ProgramData%\blazerity\bAD\logs` пусто | Смотрите `msi-install.log`, `msi-ca-error.txt` (коды `BAD_MSI_###`) и `%TEMP%\MSI*.log`. Подробности в `installer/msi/README.md`. |
| Агент не обновляется | Проверьте `update_target`, наличие версии в зеркале (раздел 5) и доступность сервера. Для ручной проверки используйте `bad update`. |
| Сертификат не применяется | Посмотрите ошибку в интерфейсе и `journalctl -u bad-tls-apply`. Боевые файлы при ошибке не меняются. |
| Устройство «устарело», хотя ПК работает | Порог «устарело» (раздел 3.6) должен быть больше интервала heartbeat. |
